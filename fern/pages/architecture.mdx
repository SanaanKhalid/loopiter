---
title: Architecture
---

Loopiter lives inside your Python or Node.js application. The Python SDK is native
and async; it does not call a Node.js subprocess. Neither SDK opens a listening server or
schedules itself. Your infrastructure owns ingestion, credentials, database, jobs,
model calls, deployments and operations. Use one SDK as the lifecycle owner for a
target: the two SDKs have separate storage contracts and are not shared-database clients.

| Layer | Responsibility |
| --- | --- |
| Namespace-bound client | Runtime validation, immutable creation, CAS updates, lifecycle coordination |
| Analyzer | Indexed joins and structured segments over a bounded snapshot of evidence |
| Controller | Calls trusted recipes/evaluators under explicit budgets and review-first policy |
| Store adapter | Atomic, durable, namespace-serializable transactions and pagination |
| Deployment adapter | Idempotent external apply/rollback, authoritative inspection and fencing |
| Application | Authorization, verified labels, scheduling, secret handling, monitoring and recovery |

## Persistent records

Executions describe decisions and their model/prompt versions. Signals attach
observations to an execution or episode. Candidates contain immutable proposed
changes and evidence. Mutable candidate records carry monotonically increasing
revisions and append evaluations; approvals reference exact evaluated content.

A target record has at most one active candidate and one pending attempt. Attempts
identify apply/rollback operations and expected external versions. Lifecycle events
are insert-only within the transition transaction. Imported legacy candidate data
is historical only, never silently active.

## Transaction boundary

1. Read and validate the candidate, evaluation, approval and target under a short transaction.
2. Reserve the target and persist a stable pending attempt plus event; commit.
3. Call the deployment adapter **outside** the transaction, with attempt ID as idempotency key.
4. Validate the receipt; atomically finalize the attempt, candidate states, active pointer and event.
5. On ambiguity, retain the reservation and inspect. Never blindly replay an external change.

Database and external operations cannot be made universally exactly-once by an SDK.
Reliable reconciliation depends on the adapter. An application-owned PostgreSQL
prompt registry in the starter demonstrates receipts and actual inference version
selection in one database transaction.

Model and deployment callbacks never run while the SDK holds a store transaction.
Analysis reads a bounded namespace snapshot; use narrow windows to keep reads short.
The reference implementation serializes namespace transactions using advisory locks;
it is correctness-first, not a claim of unlimited concurrent throughput.

Bring your own database. The core imports no driver. `loopiter/postgres` accepts a
developer-owned `pg` pool through a structural interface; install `pg` in your app.
`migratePostgres(pool)` is an explicit setup action running versioned SQL. Construction
does not connect, migrate, create a database or change customer tables automatically.
The reference SQL uses Loopiter-prefixed tables; review conflicts before adopting it.

## v3 contract (0.3 alpha)

A store exposes `version: 3`, `transaction(namespace, callback)`,
`deleteNamespace(namespace)` and `close()`. A transaction exposes generic
`get(collection,id)`, `list(collection,options)`, `insert(collection,record)` and
`replace(collection,record,expectedRevision)`.

- All reads/writes are scoped to the transaction namespace. Reject cross-namespace rows.
- Transactions are atomic and serializable within a namespace, including independent
  clients/processes. Failed callbacks commit nothing; callbacks/results cannot escape
  the transaction lifetime and mutate committed state.
- Insert is insert-only and starts at revision 1. Duplicate IDs conflict. Client-level
  creation performs content-hash idempotency before insert.
- Replace checks the current revision and requires exactly the next revision. Identity
  and namespace cannot change. Signals, lifecycle events, observations and historical records are immutable.
- List defaults to 100, maximum 1,000, with an opaque nextCursor and stable ID order.
  UTC windows use execution startedAt, signal observedAt, otherwise record createdAt;
  inclusive from / exclusive to. No silent truncation or repeated cursors.
- Namespace deletion is explicit and atomic with respect to namespace transactions.
  Stop writers and resolve pending external operations before deleting history.

PostgreSQL uses one checked-out connection for BEGIN, queries and COMMIT/ROLLBACK.
Namespace advisory locks coordinate separate pools/processes. See
[node-postgres transactions](https://node-postgres.com/features/transactions).
Model/deployment calls occur outside store transactions. `PostgresStore.close()`
does not end your pool; your application controls its lifetime.

## Conformance

```typescript
import { InMemoryStore } from 'loopiter';
import { runStoreConformance } from 'loopiter/testing';
const store = new InMemoryStore();
console.log(await runStoreConformance(store));
await store.close();
```

Run this against your adapter in an isolated test database. It creates random
conformance namespaces and deletes only those. It exercises scope, insert conflicts,
rollback, CAS races, paging, transaction lifetime and deletion. Passing this baseline
does not certify an adapter; add independent-process races, database outages,
durability and deployment fault injection against your actual infrastructure.

InMemoryStore and JsonFileStore are **development tools**. JSON uses restrictive
file permissions and atomic replacement, but no cross-process coordination. Do not
share one JSON file across production workers. No retention service is supplied.
Own backups, TLS, access control, restore drills, pool limits and migration credentials.

The new collections are `runs`, `operations`, `budgets`, `observations` and `coordination`.
Stop old writers and explicitly apply SQL `002-autonomy.sql` before using v3. JSON development
stores require an explicit copy-only `migrateJsonV2` call. See
[0.3 migration](/operate/migrating-to-0-3) for backups, preserved lineage and recovery.
